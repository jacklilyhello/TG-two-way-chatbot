## 1. 项目目标与开发范围

在全新仓库实现精简的 Telegram 双向私聊机器人，使用 TypeScript 与原生 Cloudflare 服务。

保留：

- 用户与管理员双向聊天；每个 TGID 一个当前有效的管理员 Forum 话题。
- 文字、图片、视频、音频、语音、文件、贴纸、相册等已支持消息类型。
- 有映射且 Telegram API 支持的回复引用、文本编辑、说明编辑和媒体编辑同步。
- 管理员手动封禁与解除封禁。
- 用户资料卡、/tj、/sc、/mb、独立日志话题。
- 必要的鉴权、限流、可恢复队列、异常处理和审计。

不引入人机答题、自动解封答题、RSS 订阅、Ping、NextTrace 或远程服务器管理，也不为这些功能保留模块、配置、菜单或依赖。

固定 /start、/help 仅发送管理员预设的欢迎与帮助文案。

## 2. 管理员群组与话题

每个实例继续使用各自原 Bot Token 和原管理员 Forum 群组，不跨实例共用业务状态。

| 话题 | 用途 |
|---|---|
| General 主话题 | 授权管理员执行 /tj TGID、/mb；/mb 内提供系统设置 |
| 用户独立话题 | 双向聊天、置顶资料卡、用户管理、/sc、旧话题绑定 |
| 系统日志话题 | 异常、绑定变更、删除结果异常、重要管理操作和运行事件 |

约束：

- General 和日志话题永远不能绑定普通用户。
- 日志话题初始化创建后保存 Thread ID，重启复用。
- 日志话题不参与双向聊天；管理员在其中发言不能被转发给用户。
- General 按实际群组与 Telegram 更新判断，不把示例链接中的 /1 当成所有 API 调用都应填入的线程参数。
- 机器人需要相应的话题管理、置顶等权限；反应必须在群组允许范围内。
- 管理命令和按钮都检查管理员身份、实例、群组、话题及目标用户；不能只依赖隐藏菜单。

## 3. /tj：注册、旧话题绑定与冲突

### 3.1 在 General 注册

授权管理员发送 /tj TGID：

1. 检查参数和身份。
2. 已有有效绑定时返回现有话题，不重复创建。
3. 未注册时记录用户与首次进入新系统的时间。
4. 尝试获取姓名、用户名和头像；不可取得时用 TGID 占位。
5. 创建用户话题、用户资料卡并置顶，保存映射及卡片 ID。

首次联系字段沿用已确认定义：第一次管理员注册或第一次进入新系统的时间。重复注册、资料更新和绑定切换均不重置它。

### 3.2 在旧话题绑定

在旧用户话题发送 /tj TGID：

- 当前话题未占用且用户未绑定时，直接绑定当前话题。
- 保留现有管理员历史，不创建替代话题。
- TGID 已绑定当前话题时幂等处理。
- 用户已绑定 A，而当前 B 未被其他用户占用时，显示确认切换/取消。
- 未确认前仍使用 A；确认后有效绑定转至 B，A 保留但停止普通消息转发。
- B 已绑定另一个 TGID 时拒绝操作，不能附带解除另一用户的绑定。
- 确认时重新验证现状；过时的确认按钮不得覆盖后续绑定变化。
- 保留审计；旧资料卡按钮失效或重新验证；在旧话题继续发普通聊天消息时提示当前有效话题。
- 保留新数据库中已经积累的消息映射，不因切换删除它们。

两个已知旧对话应优先手工登记；未登记用户主动联系时，系统无法从全新数据库识别其旧话题，可能先建新话题，之后仍可确认切回。

### 3.3 资料与可联系性

用户再次主动联系时更新姓名、用户名、可取得的头像和资料卡，保留首次联系时间及有效绑定。

注册成功不等于能够主动私信。普通机器人不能仅凭一个从未建立过私聊的 TGID 发起对话。保留原 Token 不会因为更换运行平台而自动要求所有既有用户重新 /start；仍以 Telegram 实际权限与接口结果为准。

## 4. 双向消息、引用和编辑

### 4.1 用户发往管理员

处理顺序：

1. 可靠记录更新及用户端原消息 ID。
2. 检查管理员手动封禁；被封禁用户的消息不转发，用户端保持静默。
3. 按消息类型向当前有效话题投递。
4. 保存消息映射、实际投递结果和必要日志。

普通用户不接收投递成功/失败、封禁状态或内部异常提示。除主动触发固定 /start、/help 外，不生成自动聊天回复。

### 4.2 管理员发往用户

只有授权管理员在当前有效用户话题的业务消息才能转发。系统消息、管理命令、日志和资料卡不能被当作聊天内容转发。

| 结果 | 管理员侧反馈 |
|---|---|
| Telegram API 确认投递成功 | 原消息显示 👍 |
| 明确被用户拉黑 | 对方已拉黑机器人 |
| 明确未送达 | 未送达，请重试；能够确定原因时补充具体原因 |
| 结果未知或其他异常 | 发生未知情况；结果未知单独记账 |

已投递不表示已阅读。Forbidden 等通用异常不直接等同于拉黑。

消息发送与状态标记分别记录：发送成功但反应失败，仍属于发送成功，另报标记异常，不能重发聊天内容来修复表情。

### 4.3 引用与编辑

- 引用仅映射到正确用户、正确方向的已知目标。
- 无映射、目标删除或接口不支持时，降级为普通消息并向管理员记录原因。
- 用户编辑原消息时只更新管理员侧机器人副本；管理员编辑原消息时只更新用户侧机器人副本。
- 不通过机器人改写管理员或用户本人发送的原件。
- 用户编辑仍检查手动封禁与当前绑定；被封禁期间不把编辑同步给管理员，保留已有管理员副本。
- 已被 /sc 删除的消息不因后续编辑重新发送。
- 新消息、编辑和删除按同一用户的顺序协调，避免旧编辑覆盖新内容。

## 5. 相册与反应：已确认 ①A

Telegram 相册反应不能逐张独立标记，因此：

- 相册逐条保存消息 ID、映射及实际结果。
- 整组投递成功后显示 👍。
- 整组删除成功后显示 👎。
- 部分发送失败或部分删除时，管理员侧显示明确文字摘要，不用单个表情冒充整组结果。
- /sc 只删除被回复的那一条映射对应的用户侧消息，不扩展成删除整组。
- 普通单条消息删除成功仍不额外发送成功文字；相册部分结果是已确认的例外。
- 反应设置失败不改变已经确认的发送或删除结果。

## 6. /sc 与清空此对话

### 6.1 /sc 单条删除

管理员回复指定业务消息执行 /sc：

- 根据映射定位用户私聊端消息。
- 仅删除用户端实际原件或机器人副本。
- 管理员原消息、管理员历史和话题保留。
- API 确认删除后更新数据库；单条消息设置 👎 替换 👍。
- 不改成删除线，不补发管理员原消息副本。
- 映射缺失、超过时限、API 拒绝、结果未知分别记录，不伪报成功。
- 重复操作读取已确认状态，尽量幂等处理。

删除受 Telegram API 实际规则约束，不能把“48 小时内”理解成绝对可删。无法找到消息时也不能凭空断言是本次操作删除成功。

### 6.2 清空此对话

- 资料卡点击后先显示确认/取消。
- 确认时确定操作范围，不把随后刚到的新消息自动纳入本次清空。
- 范围为新系统已经记录的该用户私聊消息，含收到后因手动封禁未转发或转发失败的用户原消息。
- 逐条保存实际结果；有管理员对应消息时更新反应，相册按第 5 节处理。
- 管理员侧任何历史消息均不得因清空被删除。
- 返回已确认删除、未删除及原因、结果未知等实际摘要。
- 废弃数据库时期未记录的私聊数量未知，显示“无法追溯/数量未知”，不能编造一个历史条数。
- 不扫描未知历史，不把仅修改数据库状态当作 Telegram 删除成功。

## 7. 用户资料卡与固定文案

每个有效用户话题有一张当前有效的置顶资料卡：

- 姓名：First Name 与 Last Name 拼接，未知时 TGID 占位。
- TGID。
- 用户名；无用户名显示“未设置”。
- 首次联系。
- 通用、苹果、安卓三个蓝色入口；使用有效 Telegram 链接或可用降级方式，不编造用户名，不能承诺绕过用户隐私或所有客户端限制。
- 可取得时展示头像。

按钮：
封禁/解除封禁、直达对方主页、清空此对话。

保持单个当前有效卡片并更新数据；绑定切换后避免旧卡片继续控制过时对象。

已确认 ②A：

- 保留 /start、/help 固定欢迎/帮助文案。
- 各实例文案独立，保留原有姓名/用户名变量需求。
- 普通聊天不触发自动回答。

## 8. /mb：统计与系统设置

仅在管理员 General 主话题授权使用。

统计包括：
总注册用户、当前封禁人数、总消息量、今日消息量、管理员发送成功与失败、成功率、未送达、结果未知/其他异常和活跃用户。

时间范围：
今日、最近 7 天、最近 30 天、全部。
默认按 Asia/Singapore 展示，最近 7/30 天含今天，底层保存 UTC。

统一口径：

- 总消息量统计新系统收到的双向业务原消息；相册按实际条数。
- 命令、资料卡、日志、状态提示、重复更新和重试不计入原消息量。
- 编辑独立记事件，不重复增加原消息数量。
- 管理员发送成功率 = 成功 /（成功 + 明确失败），按业务消息去重，未知结果单列。
- 活跃用户为所选范围内主动发送业务消息的不同 TGID 数。
- 不推算、不导入、不伪造旧系统历史统计。

用户管理支持：
列表分页、按 TGID 查找、用户详情、状态、消息统计、绑定信息和话题跳转。

已确认 ③A：

- /mb 保留系统设置，管理固定欢迎/帮助文案、时区等本项目已有非密钥设置。
- Bot Token、Webhook Secret 保存在各实例 Secrets 中，不在群内展示。
- 不恢复被删除的旧业务设置入口。

## 9. 数据库与可靠性

每个机器人使用全新、独立的 D1 数据库。
建议核心业务结构：
users、user_threads、message_mappings、delivery_events、user_policies、bot_settings、audit_logs。

为满足已确认修订，还需要可靠记录：

- 所有已收到的用户端消息，而非只记录成功转发映射。
- 更新去重键、处理状态、消息版本、相册成员。
- 待处理任务、重试、结果未知、恢复进度。
这些可在合理的数据表设计中实现，不要求机械地限定表的数量。

数据约束：

- TGID 和当前有效话题映射唯一。
- 一个话题不能同时有效绑定多个 TGID。
- General、日志话题保留为系统用途。
- 绑定切换、按钮确认、编辑和删除检查当前状态，避免过时操作。
- 消息发送、编辑、删除、反应分别记录，不能相互混淆。
- 同一用户任务显式串行协调。
- 待处理任务持久化，Worker / DO 重建后恢复。
- 明确限流等可安全重试的情况自动重试；已发出但结果不明的发送请求不得盲目重发。
- Telegram 外部副作用与数据库之间不是一个事务，不能承诺绝对“恰好一次”。

旧数据库：

- 不导入，不用于运行时恢复话题或消息映射。
- 上线前独立备份旧库。
- 旧用户和旧话题通过 /tj 手工重新登记。
- 新系统上线后新积累的数据，应正常持久化和备份，不能把“废弃旧库”理解成每次升级清库。

## 10. 日志、错误与权限

- 日志记录封禁操作、重要投递失败、删除异常、绑定变更、管理操作和运行异常。
- 日志话题不可用时先持久保存，恢复后补报。
- 运行日志采用部署、版本、异常与恢复事件；不依赖常驻进程启动/关闭通知。
- 限流和告警需协调，不能让重复日志占满聊天发送能力。
- 话题创建结果未知时，不盲目不断重复创建。
- 状态未知必须保留，不能强行归为成功或失败。
- 管理鉴权沿用明确 TGID，命令和按钮均校验。
- 任何密钥、Bot Token 及含密钥的请求 URL 不进入公开日志。
- 不把管理员侧消息删除作为数据库写入失败的默认补偿办法。

## 11. 原生 Cloudflare 技术架构

| 组件 | 用途 | 本版选择 |
|---|---|---|
| TypeScript Worker | Webhook、队列消费、系统恢复入口 | 每 Bot 独立部署；原生 fetch 调用 Telegram |
| D1 | 用户、绑定、消息记录、任务、设置与审计 | 每 Bot 独立数据库；版本化 SQL migrations |
| Queues | 异步唤醒、缓冲、重试调度 | 每 Bot 独立任务队列；消息只携带任务标识与必要元数据 |
| Dead Letter Queue | 超过自动处理预算的队列任务 | 每 Bot 独立；业务任务仍在 D1，可诊断与有条件重驱动 |
| Durable Objects | 同一用户操作协调、相册聚合、Bot 级限流 | 各 Bot 独立命名空间；协调器的恢复信息持久化 |
| DO Alarms / Cron Triggers | 分批续跑、重试到期唤醒、遗漏任务修复 | 事件驱动为主，定时恢复兜底；不使用常驻循环 |
| Worker Secrets | Bot Token、Webhook 密钥 | 每 Worker 单独配置，不进 D1 设置页或公开仓库 |
| Workers Logs + D1 审计 | 技术排障与业务追踪 | 技术日志脱敏；重要业务审计不能只依赖短期平台日志 |
| R2 | 可选长期备份 | 启用时每 Bot 独立私有桶；核心聊天流程不依赖 R2 |

同一 Worker 部署可以同时提供 fetch、queue、scheduled 入口并导出 Durable Object 类。无需为了这些职责额外部署几个共享业务 Worker；每个机器人仍是一份可独立发布的服务。

本版不引入常驻 Node 服务、Redis、外部业务数据库或网页管理后台。管理界面继续使用 Telegram 的话题、按钮与 /mb。

### 11.1 每个机器人完全独立的具体含义

| 边界 | 机器人 A | 机器人 B |
|---|---|---|
| Worker 名称 | tg-two-way-a | tg-two-way-b |
| D1 | tg-two-way-a-db | tg-two-way-b-db |
| 任务队列 | tg-two-way-a-jobs | tg-two-way-b-jobs |
| 失败队列 | tg-two-way-a-dlq | tg-two-way-b-dlq |
| 用户协调命名空间 | A 的 ConversationCoordinator | B 的 ConversationCoordinator |
| 实例协调命名空间 | A 的 BotCoordinator | B 的 BotCoordinator |
| Token / Webhook Secret | A 自己的 Secrets | B 自己的 Secrets |
| Telegram 群组、日志话题、文案 | A 自己的设置 | B 自己的设置 |
| 数据迁移、版本与恢复 | A 独立选择版本和执行 | B 独立选择版本和执行 |
| R2（如启用） | A 独立私有桶 | B 独立私有桶 |

以上均为资源命名示例，尚未创建。共享的只有源码和可复用构建产物；不部署一个总 Worker 按 Token 分流，也不使用一个总 D1 靠 bot_id 区分全部机器人。

实例配置必须显式列出资源，不能让 B 默认继承 A 的数据库、队列或 Secrets。部署前核对 Bot 身份与预期 Bot ID，拒绝把同一 Bot Token 同时用于两个活动实例。开发、测试和生产使用各自资源；测试 Bot 不使用生产 Token。

独立资源实现业务、数据和发布隔离。同一 Cloudflare 账户仍共享部分配额、账单和账户级故障风险；需要账户级隔离时可把同一套实例模板部署至不同账户，但本版不把多账户作为前置要求。

## 12. 消息可靠性与处理顺序

### 12.1 更新接收：先持久保存，再确认 Telegram

1. Webhook 校验 HTTPS 入口、路径、请求类型与 X-Telegram-Bot-Api-Secret-Token，限制请求体大小。入口不放需要交互登录的页面。
2. 校验更新基本结构，在 D1 保存 inbox 记录，以 update_id 唯一约束去重；记录源 chat_id、message_id、更新时间、原始类型及处理所需字段。
3. 使用 D1 支持的事务批处理，同时写入接收记录、初始任务和待调度记录。涉及用户原消息的记录在检查手动封禁和转发前落库。
4. 事务提交后尝试通知 Queue。Queue 发送失败时，D1 待调度记录仍保留，恢复任务继续补发。
5. 只要更新和后续任务已可靠提交，即可返回 200；持久提交失败则返回失败，让 Telegram 重试。不能只调用 waitUntil 或启动内存 Promise 就当作已接收。
6. 重复更新返回已接收结果，不重新生成业务消息、统计或管理员提醒。

Webhook 不等待媒体转发或大批删除。Queue 不是唯一记录来源；更新一经确认，其处理进度必须能够从持久状态恢复。

### 12.2 D1、Queue 与 DO 的职责边界

D1 保存业务事实和任务账本，是恢复与统计的依据。Queue 只负责唤醒处理；队列重复、乱序或消息过期均不能直接改变业务事实。DO 保存必要的协调进度、在途操作标识和唤醒时间，内存仅作为缓存。

每个 TGID 由对应的 ConversationCoordinator 协调，新消息、编辑、删除、清空与绑定切换检查同一用户的当前状态。General 命令按目标 TGID 路由；涉及话题占用的跨用户冲突由 D1 唯一约束和条件更新保护。

Queue 消费者不直接按“拿到哪个先发送哪个”执行，而是唤醒协调器。协调器从 D1 查找该用户最早可执行任务，检查前置依赖、源消息版本、删除状态及绑定版本，再执行下一步。

具体顺序规则：

- 用持久任务序号表示新系统接收顺序；不宣称它天然等于 Telegram 原始产生顺序。
- 不等待 update_id 连号；不同类型更新或长时间无更新都可能存在间隔。
- 编辑早于原消息处理时先等待依赖；同一源消息以 edit_date、update_id 等版本信息防止旧编辑覆盖新编辑。
- 相册有持久聚合窗口和成员记录；迟到成员需继续登记、处理并重新计算摘要，不能丢弃。
- 绑定切换确认前重新检查占用和版本；投递前重新检查当前有效话题。
- 已确认删除或被清空任务锁定的消息不能由重试、旧编辑或迟到任务重新发送。
- DO 的异步请求可能交错；代码必须实现显式队列和状态检查，不能把“单对象”当成自动业务串行。

首次新用户话题创建、资料卡、日志话题初始化也作为可恢复步骤。API 已成功但返回信息无法持久保存时保留未知状态；不能靠不断新建或删除管理员历史进行补偿。

### 12.3 外部请求与结果状态

任务与外部操作分别记录，例如：待执行、执行中、等待重试、已完成、需处理；以及 Telegram 操作的未发出、已发出、确认成功、明确失败、结果未知。

- 调用 Telegram 前持久记录 attempt_id 与请求阶段。
- 取得明确成功响应后保存目标消息 ID、映射与结果；反应另起可重试任务。
- 明确限流时按 retry_after 延后，保留任务，不用忙等。
- 请求已发出但连接中断、超时或 Worker 被中止时，恢复后按结果未知处理。
- 已成功却写库失败时尽力保存返回信息并重试落库；结果不可恢复时进入未知处理，不能重新发送来“修复”。
- 发送、创建话题等可能产生重复内容的操作，未知结果不得自动重发。
- 未知删除不计作本次删除成功。后续确认消息不存在，也不伪造此前具体删除行为。
- 队列重复消费、DO Alarm 重试和管理员重复点击均先查持久状态。
- 未知结果需要管理员查看记录并明确处理；只有确认安全的任务才能再次驱动。

Telegram API 副作用、D1 写入和队列确认不在同一个事务内。验收目标是可恢复、去重、防止盲目重发和准确记账，不承诺跨系统绝对恰好一次。

### 12.4 分批任务与恢复

清空、日志补报、相册收集、资料卡修复、备份等工作均采用有界批次，保存游标或快照，使用 Alarm 或后续任务续跑。不得依赖一次超长 Webhook 完成所有工作。

建议以一分钟级、带索引的有限扫描作为待调度任务恢复兜底；空闲时只检查少量待处理记录。它是系统可靠性机制，不恢复已删除的 RSS 或 Telegram 长轮询功能。

Queue 消息可以在对应工作已完成，或下一步已可靠保存并具备恢复入口后确认。失败队列记录 task_id 和原因；其被消费不等于业务已完成。人工重驱动仍必须经过幂等与未知结果检查。

## 13. Telegram 平台适配

### 13.1 媒体转发

支持的文字、图片、视频、音频、语音、文件、贴纸和相册优先使用 Telegram 复制能力或同一 Bot 的 file_id。不同 Bot 的 file_id 不混用。

- 不通过 Worker 下载并缓存整个大视频或文件后重新上传。
- 引用、说明、文本实体及相册成员映射在适配层单独处理。
- 相册记录每一条的实际发送返回值，不能只保存一个“整组成功”字段。
- 若批量复制返回值不足以可靠对应输入成员，不猜测映射；选用能确定对应关系的发送路径或进入明确异常处理。
- Telegram 不支持复制、发送或编辑的消息，给管理员可理解的失败或降级说明，不向用户泄露内部状态。

Webhook 里只接收更新元数据；媒体二进制不塞入 Queue 或 D1。Workers 的内存有上限，不能把自动扩容理解成单次请求拥有无限内存。

### 13.2 限流和管理员反馈

BotCoordinator 对每个 Bot 的出站请求协调发送额度，尤其关注整个管理员群组的合计消息。不同 Forum 话题不能视为各自拥有一份独立群组发送额度。

聊天、状态反应、资料卡更新、日志与告警分配处理优先级。避免为每条重复异常生成大量新日志；事件仍逐条入库，通知可合并。各操作按 Telegram 实际 429 和 retry_after 调整。

限流会造成排队延迟；不通过无休止并发或放弃记录来追求表面实时性。

## 14. D1 数据设计

以下为逻辑结构，实施时可以合理合并，但不能删掉对应能力。

| 表或表组 | 主要职责 |
|---|---|
| users | TGID、姓名、用户名、头像信息、首次进入新系统时间 |
| user_threads | 当前有效绑定、历史绑定、状态与版本 |
| user_cards | 当前资料卡消息 ID、版本、置顶与修复状态 |
| user_policies | 手动封禁、操作者与更新时间 |
| bot_settings | 时区、固定文案、日志话题 ID 等非密钥设置 |
| inbox_updates | update_id 去重、接收信息、处理所需载荷与进度 |
| messages | 双向消息记录、业务/系统类型、用户端可删除目标、编辑版本、时间与删除状态 |
| message_mappings | 源与目标消息对应、方向、用户、线程和复制关系 |
| media_groups / media_members | 相册成员、聚合状态、逐条结果 |
| jobs / outbox | 任务序号、前置依赖、状态、下一次执行时间、调度恢复 |
| operation_attempts / delivery_events | 外部调用阶段、尝试记录、已知返回值与成功/失败/未知 |
| deletion_batches / deletion_items | 清空确认快照、逐条删除结果、续跑游标 |
| callback_actions | 一次性确认、目标、管理员、绑定版本、有效期 |
| audit_logs / log_outbox | 管理操作与可靠日志补报 |

关键约束：

1. 单 Bot 数据库内 update_id 唯一；源消息使用 chat_id + message_id + 方向等正确的组合键。
2. 每个 TGID 只能有一个当前有效用户话题；每个用户话题只能有效归属一个 TGID。
3. 历史绑定和消息映射保留；不得用覆盖唯一当前值的办法丢掉切换历史。
4. 消息接收、投递、编辑、删除和反应使用独立状态，原始业务计数不随重试增长。
5. 保存 UTC；展示、统计窗口按实例时区计算。
6. 业务更新采用 D1 支持的事务批处理、唯一约束和条件更新；不假设可以跨任意网络调用保持 SQL 事务。
7. 对 TGID、源/目标消息、当前绑定、时间范围、任务状态与执行时间建立必要索引。
8. 关键权限、绑定与任务状态读取使用保证新鲜状态的访问方式；首版不引入读副本带来的额外一致性路径。
9. 数据库 migration 与 Worker 版本关联；普通升级只做兼容迁移，不清库。
10. 待完成任务不能清理；影响引用、删除、统计和审计的业务记录不默认自动过期。后续容量增长再明确归档政策。

所有已接收的私聊消息及机器人发出的私聊消息均保存用户端消息 ID，包括固定 /start、/help 的回复，便于清空时覆盖已知范围；命令与固定文案仍不计入业务消息量。

不为保存业务正文无限复制多份载荷。完成后的更新原始载荷与长期业务记录可以分层管理，但任何自动清理周期必须在实施文档中明确，并保证不破坏上述需求。

### 14.1 清空时的特殊一致性

清空确认在持久事务中捕获该用户当时已知消息集合和入站任务边界。执行中的发送须先记录实际结果；边界内尚未发送的旧任务标记为不得再次投递。

快照范围内，如果管理员发送请求已经发出，待返回后把新得到的用户端消息 ID 归入该清空任务；若发送结果未知，清空摘要同样保留未知项。确认后新收到的业务消息不属于本次范围。

这样既不误删刚来的新消息，也不让确认前积压的旧内容在清空完成后再次出现。所有管理员历史仍然保留。

## 15. 配置、Secrets 与运维入口

### 15.1 配置分层

| 层级 | 内容 | 管理方式 |
|---|---|---|
| 实例部署配置 | 实例名、预期 Bot ID、管理员群组、管理员 TGID、资源绑定 | 每实例私有配置；仓库提供占位模板 |
| Worker Secrets | TELEGRAM_BOT_TOKEN、TELEGRAM_WEBHOOK_SECRET | Cloudflare Secrets；本地仅用被忽略的测试配置 |
| D1 设置 | 文案、时区、日志话题 | /mb 管理非密钥选项，修改留审计 |
| 构建与发布配置 | compatibility_date、依赖锁定、实例配置清单 | 仓库版本化；生产绑定显式选择 |

仓库是公开的，真实 Token、Webhook Secret、部署凭据和含敏感信息的实例配置不提交。日志统一去除认证头、Secret、含 Token 的 URL 和错误堆栈中的敏感参数。

Telegram API 目标由程序固定或受控配置；不提供让普通聊天内容任意指定请求目标的功能。

### 15.2 健康检查与运行事件

健康入口只返回必要的可用状态和版本，不暴露用户列表、环境变量、配置或数据库详情。数据库、积压、未知结果和日志投递异常通过内部监控与管理员日志追踪。

Worker 没有可靠的一次性常驻进程生命周期。“启动/关闭通知”调整为部署版本、Webhook 状态、首次初始化、异常、积压和恢复通知，不在每个请求进入时发送“启动”。

日志话题删除或不可写时，事件先留在 D1；管理员恢复权限或指定有效日志话题后续报。无法实时保证崩溃时发出通知，也不把日志发送成功当作业务处理成功的前置条件。

## 16. 备份、恢复、套餐与费用

### 16.1 备份与恢复方案

- 每个 Bot 使用自己的 D1 恢复能力与数据迁移记录。
- D1 Time Travel 当前窗口为免费计划 7 天、付费计划 30 天；上线前核对实际账户能力。
- 长期备份采用独立私有 R2 桶作为可选扩展；保留周期尚未设定，不默认无限期保存，也不默认自动删除重要业务数据。
- 首次生产上线前，在测试资源验证恢复步骤与版本兼容性。
- 恢复或回滚前暂停该实例的出站消费，核对在途请求、队列、DO 协调状态与 D1 任务状态。
- D1 回退不会同时回退 Queue、DO 或 Telegram，不能一恢复数据库就盲目重放旧任务。
- 恢复后对旧任务使用恢复边界或代次标记进行隔离；已知完成的不重复执行，外部结果不明的进入人工核查。
- 数据库恢复不能撤销已发送的消息，也不能还原 Telegram 已删除的私聊内容。

暂未启用 R2 时，仍应提供受控的数据导出与恢复操作文档；不能把代码版本回滚等同于业务数据备份。

### 16.2 费用与容量

依据 2026-10-11 核对的官方文档：

- Workers Paid 的账户最低费用为每月 5 美元，并非每个机器人 5 美元。
- D1、Queues、Durable Objects 和可选 R2 按各自规则计量；5 美元不是完整系统的费用上限。
- 免费额度可用于验证；生产建议以 Workers Paid 评估和验收，不承诺免费套餐足以长期承载。
- D1 免费账户最多 10 个数据库、单库 500 MB；付费单库上限 10 GB。测试环境也计入资源使用。
- 多个 Bot 同账户仍受账户总额度影响；每个实例应能查看自身任务量、错误与积压。
- 最终月费需要消息量、数据库读写、任务处理量和保存期限才能估算。当前不编造“固定低价运行任意数量机器人”。

| P0：原生能力验证 | 在测试 Bot 验证 Webhook、D1、Queue、DO、媒体复制、相册与贴纸转发 | 无常驻进程或 Docker 依赖；关键 API 和媒体能力可用 |
| P1：项目与可靠任务骨架 | TypeScript、Wrangler、D1 migrations、去重、outbox、DO 顺序和 Bot 限流 | 重复/乱序/中断场景不直接重复发送；持久任务可恢复 |
| P2：聊天与绑定 | /tj、新旧话题、资料卡、普通消息、媒体、相册、引用与编辑 | 新旧话题规则、有效映射和业务转发符合第 2–5 节 |
| P3：用户管理 | 手动封禁/解禁、固定文案、日志 | 权限和状态持久化正确，用户端无内部状态通知 |
| P4：删除与面板 | /sc、清空快照、/mb 统计/设置、确认回调 | 用户端删除准确、管理员历史保留、指标可核对 |
| P5：隔离与上线准备 | A/B 实例、单独发布回滚、恢复演练、中文文档与 CI | 数据/配置/队列无串用；形成生产切换清单 |

P0 使用临时测试实例，不先接管真实 Bot。P1–P4 每完成一个可运行切片就验证关键行为；不能把故障恢复和媒体兼容全部留到最后。

GitHub 工作流：独立开发分支、提交、PR；校验类型、构建、必要行为测试与资源配置。生产发布按实例和明确版本执行，不能合并一次就自动把所有机器人同时升级。部署 Token 只通过受控凭据传入，不进入 PR 日志。

### 18.1 验收清单

1. Webhook Secret 错误时拒绝；正确更新持久保存后才确认；D1 失败时不假装成功。
2. 同一 update_id 重复到达、队列重复、任务重试不增加原消息计数，不重复正常发送。
3. 新用户并发联系不重复产生有效话题映射；话题创建结果未知时有可处理记录。
4. /tj General 注册、旧话题绑定、确认/取消、目标占用、过时确认和旧卡片处理完整。
5. 双向文字与全部约定媒体正常；相册逐条映射、迟到成员与部分结果正确。
6. 引用跨方向正确；无映射按规则降级；编辑顺序正确；已删除内容不会复活。
7. 管理员消息成功、明确失败、拉黑、结果未知分开；反应失败不触发内容重发。
8. ①A：相册 /sc 只删回复的一条，部分结果有准确摘要，不能伪装整组删除。
9. 普通 /sc 不删管理员原件，不加删除线、不补发副本；删除失败或未知不标成功。
10. 清空先确认，覆盖已知用户端原件与副本，包括手动封禁期间收到但未转发、转发失败的消息；确认后新消息不误删，积压旧消息不复活。
11. ②A：/start、/help 每实例文案独立；普通用户不接收失败、封禁或投递状态提示。
12. 手动封禁持久生效，封禁期间用户新消息与编辑不转发；所有管理命令和按钮校验授权。
13. ③A：/mb 时间窗口、统计口径、分页、TGID 查询、用户详情和系统设置正确；密钥不显示。
14. Worker/DO 被重建、Queue 乱序、D1 临时失败、API 超时与 429 都有正确恢复行为。
15. 日志话题失效时业务审计保留；恢复后补报；不形成告警发送风暴。
16. A/B 两个测试实例不能读写对方业务状态；发布、回滚、清空或故障仅作用于目标实例。
17. D1 恢复后不会盲目重放 Telegram 副作用；未知项保持可追踪。
18. 新代码仅含本规格业务；不包含人机答题、自动解封题、RSS、Ping、NextTrace、服务器管理模块或启用入口。
19. 在真实测试群实测头像/三个资料链接、话题权限、反应许可及删除限制；记录 Telegram 客户端或 API 不支持的边界。

测试重点是会导致丢消息、重复发送、误删、越权、串号或统计错误的行为；不通过单纯逐函数镜像测试制造虚假的覆盖率。

## 19. 旧机器人切换到新项目

按一个机器人一个机器人切换；无需同时迁移全部 Bot。

1. 记录该 Bot 身份、原管理员 Forum 群组、授权管理员及两个已知旧用户的话题信息。旧数据库独立备份，业务数据不导入新 D1。
2. 使用测试 Bot 完成前述验收；正式实例创建自己的 Worker、D1、队列、DO 与 Secrets，并核对资源绑定和版本。
3. 在正式切换点暂停该 Token 的旧消费者及旧出站任务，处理在途请求。停止旧进程的自动重启，防止与 Webhook 实例争用。
4. 设置新 Worker 的 Webhook，使用独立 Secret；不主动丢弃待处理更新。只订阅业务需要的更新类型，后续按需调整。
5. 核对 getWebhookInfo、权限与首条消息路径；管理员优先在已知旧话题 /tj TGID 重新登记。
6. 保留所有原有管理员话题与消息；新数据从上线时间开始累计。
7. 观察投递、队列积压、日志及未知任务；稳定后再切换下一个 Bot。

Telegram 待处理更新有平台保留期限，切换窗口应尽量短；不保证无限期离线仍不丢更新。

旧 Bot 的 Token 和原群组继续使用；不因迁平台强制所有既有用户重新 /start。但对从未建立私聊的 TGID，仍不能仅靠 /tj 保证主动投递。

### 19.1 回滚边界

正常版本回滚是在同一实例内选择兼容的 Worker 代码版本，保留业务数据并核对 schema。涉及破坏性数据库变更时，不能只回滚 Worker 代码。

本版不把重新开启旧 Docker 程序作为默认回滚方案。新系统上线后的映射、任务、未知结果和统计不会自动进入旧程序；直接恢复旧消费者可能造成重复处理与状态丢失。

上线前必须准备可用的上一份原生版本、单实例暂停消费与恢复手册。首次上线尚无上一份原生业务版本时，回退到维护状态：关闭出站处理、尽可能继续持久接收或让 Telegram 重试，保留 D1 与队列，修复后恢复。平台入站保留期限仍适用。

## 20. 当前可以定稿与后续实施输入

已经明确，不重复询问：

- 全新仓库与指定本地目录。
- 原生 Cloudflare 单一路线，无 Docker。
- 每个机器人独立 Worker、D1、任务资源及 Secrets。
- 纯双向业务范围、①A/②A、③A 的非密钥设置入口和旧库不导入。
- 原 Token、群组及管理员历史继续保留。

本方案采用的实现选择：TypeScript、D1 任务账本、Queues 唤醒、DO 顺序/限流协调、Wrangler 本地开发、按实例发布。这些用于落实上述要求，不新增业务产品功能。

实际云端验证时才需要：测试 Bot 与群组、管理员 TGID、Cloudflare 账户/套餐、实例别名。生产切换时再配置对应正式实例；密钥通过本地或 Cloudflare Secrets 安全提供，不粘贴到公开文件。

尚未指定的长期备份保留周期不影响核心开发，R2 保持可选。没有可靠业务量时不预估固定总费用。

**本版业务范围为纯双向机器人；其余已确认规则完整保留。新项目按本文件的原生 Cloudflare 架构实施。当前工作完成于方案阶段，未实施仓库修改或生产操作。**
