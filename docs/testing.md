# 测试与真实 Telegram 验收

## 本地验证

```sh
npm ci
npm run check
node --test scripts/*.node-test.mjs
npx tsc -p scripts/reliability-drill/tsconfig.json
npx vitest run --config scripts/reliability-drill/vitest.config.ts
node scripts/check-instances.mjs
npm run build
npm audit --audit-level=high
```

Worker 测试使用本地 Cloudflare 绑定与 Telegram 接口模拟，重点覆盖持久接收、去重、绑定/确认、统计、删除快照、未知结果与重建恢复。部署工具测试覆盖实例选择不匹配、资源串用、跨角色队列复用、身份/Forum/权限不符、Webhook 接管门槛、Actions-only 写入门槛、敏感 URL 脱敏及未知请求不重试。

生产准备验证使用合成身份和隔离接口，覆盖以下边界：

- `prod-support`、`prod-ad` 两份模板各自有效，与 `test-a`、`test-b` 一起通过隔离校验；相同管理员账号与不同 Forum 可以共存，共用 Forum 被拒绝。
- 仓库模板以外的实际 Worker 配置也参与查重；同 Bot、同 Forum、项目归属不明，以及误选实例、D1、队列、域名，均在资源写入或 Webhook 修改前拒绝。
- 真正首次可缺资源 ID，部分创建必须先回填已有资源 ID，已有实例升级要求精确 ID 与身份；缺失项提示只列字段和安全步骤，未知创建不重试、不清理资源。
- Actions 按实例维护锁与单一账户初始化锁共同覆盖检查和创建；初始化脚本在取得锁后重新读取实际状态，缺少锁标记时拒绝初始化。
- 错误与子进程输出不包含私有 JSON、真实身份、Secrets 或敏感 URL；测试实例模板和既有运维门槛继续通过。

部署锁的隔离测试与工作流结构检查不能替代 GitHub 调度服务的真实并发运行证据。源码检查、隔离测试、PR/main CI、云端只读配置检查及真实 Telegram 验收分别记录；未执行部署时不将 CI 通过描述为实例已上线。

模拟测试证明代码在受控响应下的行为，不能替代真实 Telegram 客户端、群组权限、媒体、API 删除限制或云端故障验收。

`tests/admission-races.test.ts` 覆盖出站前封禁、绑定切走再切回、单删最终校验，以及 Cron 恢复对原始准入与时间的继承。`tests/ingress-observability.test.ts` 检查接收/持久结果阶段和日志脱敏；`tests/ingress-scheduling-statistics.test.ts` 检查图片原子接收、慢提示让行、反应确认后十秒起算与跨日统计。外部响应与故障均由隔离替身提供，不属于真实 Telegram 压力或云平台故障证据。

性能验收分别记录首次话题建立、已有话题、空闲后首条、双向连续发送与突发输入。浏览器提交跨度、Telegram 原消息顺序、Webhook 收到时间、任务首次执行、Bot DO 等待与 API 确认时间分开记录；浏览器未达到每秒 10 条或 10 张时保留实际值。同一批次的异步浏览器提交顺序不代表 Telegram 已确认的原消息顺序，服务端顺序以保存的接收序号和消息映射核对。

隔离测试覆盖可靠提交后的非阻塞 DO Alarm 提示、Queue 提示失败、独立键同时唤醒、共享群发送额度、相册按张预留、反应独立节奏，以及从响应到达开始计算的 `retry_after`。资料卡测试覆盖首次初始化发送/置顶门槛、唯一串行维护任务、已有话题业务积压优先、头像缓存到期/强制刷新、运行中后到请求、隐私按钮明确失败降级，以及未知发送禁止重发。真实 Telegram 验收须检查首次卡片在业务之前且置顶、压力停止后所有维护任务可以推进，并从私有时间字段读回实际耗时。

`tests/topic-initialization.test.ts` 验证首次文字、图片、相册、连续消息、初始化并发、置顶限流及失败/未知结果；`tests/moderation.test.ts` 验证状态、审计和通知的原子提交、重复动作、解除封禁与未知通知；`tests/auto-moderation.test.ts` 通过实际接收与处理入口验证首条命中、媒体说明、编辑、相册后项说明、解封后恢复和用户静默；`tests/block-rules.test.ts` 验证关键词、安全正则语义、复杂度限制、持久管理、回调权限及实例边界。上述均为隔离自动化验证，不能记作真实 Telegram 浏览器通过。

`tests/moderation-recovery.test.ts` 注入发送结果或映射落库中断，并在恢复前修改规则、封禁或解除封禁；验证恢复仅补记已确认结果，未知不重发，已命中内容不因解封或规则删除复活。

安全重试的隔离用例见 `tests/delivery-retry.test.ts` 和 `tests/delivery-retry-security.test.ts`：从真实处理路径生成失败通知及按钮，覆盖单条明确 4xx 拒绝后恢复成功、再次失败、未知与相册禁用、重复点击、原子预约竞态，以及 Bot 实际发出前的权限和目标重验证。还须覆盖最新重试及引用降级成功后映射写入中断、`/sc` 恢复私聊目标、清空快照阻止已预约重试，以及旧任务不能覆盖较新的成功。

清空让行用例见 `tests/clear-latency.test.ts`：让删除 API 推进虚拟时间，核对真实协调器在完成当前项后先执行排队中的有效按钮与新消息，再继续原快照；在逐项结果保存和续跑入队处分别中断，核对未知删除不重发、最后一项不遗漏、确认后消息不被删除。真人验收需另记按钮等待与实际清空耗时，不能用虚拟时间替代。

`tests/receipt-priority.test.ts` 使用实际 Bot 协调器和模拟 Telegram 响应验证到期清理优先、失败/删除标记不受该优先级延迟，以及未来重试、失效版本、旧恢复代次和失去调度进展的清理任务不会永久阻塞新成功标记。限流仍可使成功标记实际保留超过 10 秒；真实验收记录成功设置、计划清理、实际确认清理三个时间，不能用定时任务已入队代替实际取消证据。

已有用户绑定和话题的首次测试消息属于已有会话。若没有在授权范围内安全复现缺绑定初始化，则明确保留真实冷初始化未验证的限制，并用隔离测试核对“话题创建、资料卡发送、确认置顶、业务投递”的顺序；不得清表、导入旧库或新增未经授权的账号来制造首次联系。

## 独立测试资源

使用两个不同测试 Bot、两套独立 Forum 与实例资源；授权管理员账号允许相同。现有 `test-a`、`test-b` 的 Environment、线上资源、数据和历史继续保留，正式实例另建。真实测试身份和群组只放私有 Environment。测试消息与删除范围仅限测试数据；不得清空真实用户私聊或管理员群组历史。

每次验收记录部署 SHA、实例别名、对应 Actions run 与实际结果到 PR 描述/评论，不把真实配置、消息正文、私聊身份或操作日志提交到仓库。区分模拟、云端配置读取、真实 Bot API 交互与人工 Telegram 客户端检查，未做的项目明确保留未验证状态。

## 广播验收边界

广播功能的发布和真实测试只允许 `test-a`、`test-b`；不得部署、暂停、恢复或修改正式实例，也不得向正式 Bot 的全体用户发送测试内容。仅使用 Codex 内置浏览器中已有且得到明确授权的管理员与普通测试账号，不新增账号、不提升普通账号权限，不通过其他客户端、脚本登录或 API 模拟用户操作替代浏览器验收。

测试实例必须在各自 Environment Secret 配置 `BROADCAST_TEST_RECIPIENT_IDS`，值仅包含当前授权账号；通过 Actions 安装为同名 Worker Secret。此名单只缩小当前实例的合格用户范围，不能以测试实例注册人数较少为由忽略名单。缺失或无效时应不发送。正式实例配置此测试 Secret 应在任何外部请求前拒绝。真实名单值、身份和私有配置不得进入源码、文档、PR 或日志。

每次实际发送前，先只读核对预览冻结名单中名单外人数为零，再由浏览器完成两次独立确认。保留已有用户、绑定、规则和历史；不能通过封禁其他真实用户、删除注册记录或清表来缩小验收范围。临时草稿和经批准的测试状态应在结束后恢复，广播账本保留以供去重和核查。

| 真实内置浏览器场景 | 应观察的结果 |
| --- | --- |
| General `/mb` →“管理员广播” | 仅授权管理员可进入，目标 Bot 和接收人数清楚 |
| 纯文字、纯图片、文字加图片 | 收集、完整预览及普通测试账号实际接收一致；超过图片说明上限的图文两部分均不遗漏 |
| 未确认、仅第一次确认、取消 | 用户均未收到广播；第一次按钮重复点击不进入正式发送 |
| 两次有效确认、开始按钮连续点击 | 一份广播只发送一次；内部提示和按钮不混入用户正文 |
| 修改内容、返回预览、使用旧按钮 | 旧确认失效，重新预览且重新确认两次后才发送 |
| 普通账号、其他管理员或其他流程 | 普通账号保持静默，不能创建或确认；不同管理员及流程不串内容和确认 |
| A/B 实例隔离 | A 的草稿、范围、确认及发送不影响 B；分别核对实际收件 Bot |
| 广播期间双向聊天和管理按钮 | 原有聊天继续投递，面板可用，结果摘要不冒充聊天内容 |
| 查看和刷新结果 | 预计人数、成功、失败、未发送、未知与部分内容确认符合实际；入队不计成功 |

较大批量、伪造或并发回调、明确失败、429、网络未知、结果落库中断、通知失败、队列重复、Worker/DO 重建及重新部署使用隔离自动化补充。覆盖超过异常重试阈值人数的广播后发生暂时故障仍可继续、已确认部分不重发、未知部分不盲目重发、发送前封禁或失去绑定、测试名单缩小，以及广播和清空快照并发。长时间模拟广播请求期间，正常业务与按钮应能通过独立通道处理，同时继续共享实际限流预算。无法安全复现的真实故障如实标注；不能把模拟响应或云端只读核查写成真实浏览器验收通过。

## 业务验收

| 场景 | 应观察的结果 |
| --- | --- |
| 错误 Secret、无效 JSON、超大请求体 | 拒绝；合法更新持久提交后才确认；D1 故障不能伪报接收成功 |
| update/Queue 重复、乱序、DO 重建 | 不重复业务计数；按同用户持久任务顺序恢复，不因队列顺序误处理 |
| General `/tj`、旧话题绑定、切换/取消、占用 | 幂等；确认重新校验；General/日志话题禁绑定；保留历史和映射 |
| 资料变化、头像和三个资料链接 | 资料卡更新并置顶；首次联系不变；隐私/客户端限制如实说明 |
| 双向文字和全部约定媒体 | 实际投递、引用方向、逐条相册映射正确 |
| 编辑先于发送、编辑与删除并发 | 不覆盖较新内容，删除后不复活；不改管理员本人原件 |
| 成功、明确失败、拉黑、超时、429 | 分别记账；未知不自动重发；429 按平台返回延迟 |
| 单条明确失败通知的“重试此条” | 仅原消息发送者且仍有管理员权限可以使用；同一原消息失败后确认成功，原失败记录保留，不增加业务消息数；未知与相册没有按钮 |
| 反应失败 | 原发送/删除结果保留，只修复反应，不重发聊天 |
| 成功 👍、失败 😢 与删除 👎 | 成功设置后计划保留 10 秒，实际清理时间单独记录；失败超过 10 秒仍保留；成功后立即 `/sc` 的 👎 不被旧清理清除 |
| 相册部分失败与 `/sc` | 摘要准确；单条 `/sc` 不扩展整组 |
| 清空确认前后新消息/积压/在途发送 | 快照覆盖已知私聊含封禁/失败/固定文案；新消息保留，旧积压不复活；管理员历史完全保留 |
| 封禁、伪造管理员/群组/按钮、过时卡片 | 用户静默；服务端拒绝越权或过时操作 |
| `/mb` 今日/7/30/全部与时区 | 按 UTC 原始记录与展示时区核对；重试/编辑/系统消息不计原消息量；未知独立列出 |
| 日志话题暂时不可写后恢复 | 审计保留、恢复后补报，无重复告警风暴 |

失败转成功的真人验收只使用授权测试账号和测试消息：普通测试账号先拉黑对应 Bot，管理员发送一条可识别的业务消息，确认私聊未收到且原消息保留 😢 超过 10 秒；随后普通账号解除拉黑，由发送原消息的管理员点击原失败通知的“重试此条”。核对用户只收到一份、原管理员消息变为 👍、最终清除的是 Bot 自己的成功反应，并核对原失败账本仍在。未知请求、伪造回调和数据库写入竞态用隔离测试补充，不冒充真人验收。

## 云端隔离与恢复验收

1. A/B 两个实例分别发送可区分的测试消息，核对其 Worker 版本、DB ID、Queue ID、DO namespace 均独立；操作 A 不改变 B 的消息、设置或积压。
2. 仅升级 A，检查 B 的 Worker 版本与业务状态保持一致；A 暂停期间入站仍可靠保存，恢复后按账本处理。
3. 在测试资源模拟请求已发出后中断、D1 结果写入失败、Queue 通知失败、Worker/DO 重建，核对没有盲目重复 Telegram 副作用。
4. 导出并解密测试数据库，核对 schema/业务/任务/操作账本完整；备份仅以加密形式离开 runner。
5. 在测试实例执行受控 D1 恢复演练，核对暂停闸门、全新恢复代次、旧任务隔离及未知项保留，最后再显式恢复。不能把单纯恢复 SQL 或 `/health` 200 当作恢复验收。

最终检查应与 [V4.0 验收清单](requirements-v4.md#181-验收清单) 对照。只有真实证据支持的项目才能报告完成。

### 现存未解决与未验证边界

部署准备流程不解决慢请求、旧三张图片去向未知、新图片迟到等业务问题，隔离测试通过也不能证明这些问题已恢复。真实冷初始化、删除时限外的消息、超过 8 名用户的分页、真实故障结果和精确客户端时序仍未验证，须另取对应验收证据。生产准备不包含新一轮真实压力测试，不使用生产 Bot 发送合成测试消息；源码检查、隔离测试和 CI 通过均不代表生产已经部署。

### 独立云端可靠性演练

`Isolated cloud reliability drill` 工作流只接受两个授权测试别名和通过 main CI 的完整 SHA。显式选择创建合成资源后，它在所选测试域名的精确 `/__reliability-drill` 路径临时运行专用 Worker，使用新的 D1、Queue 和 DO；不会绑定业务实例的存储或加载真实 Telegram Token。入口带临时授权密钥，演练代码没有外网转发后备路径，使用独立持久 DO 作为 Telegram 接口替身。

演练覆盖云端绑定层注入的 D1 接收失败、Queue 通知失败、429 延迟、D1 结果落库失败、实际 DO 中止/重建、未知结果不重发和第二次 Worker 部署后的持久记录。D1/Queue 异常来自受控绑定适配器，不表示真的制造了 Cloudflare 平台故障；接口替身结果也不属于真实 Telegram 业务验收。

结束时只移除本次创建且读回确认归属的精确临时路由，保留合成持久资源供核查，Worker 的 workers.dev 和预览地址均禁用。失败或中断后先检查聚合 artifact、精确路由和命名资源，不得把另一次运行当作此前未知写操作的重试。数据库恢复另用[测试恢复工作流](operations.md#独立测试实例恢复工作流)，真实双向消息另用上述浏览器验收清单。
