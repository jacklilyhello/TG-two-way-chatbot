# 测试与真实 Telegram 验收

## 本地验证

```sh
npm ci
npm run check
node --test scripts/deployment.node-test.mjs
node scripts/check-instances.mjs
npm run build
npm audit --audit-level=high
```

Worker 测试使用本地 Cloudflare 绑定与 Telegram 接口模拟，重点覆盖持久接收、去重、绑定/确认、统计、删除快照、未知结果与重建恢复。部署工具测试覆盖实例选择不匹配、资源串用、跨角色队列复用、身份/Forum/权限不符、Webhook 接管门槛、Actions-only 写入门槛、敏感 URL 脱敏及未知请求不重试。

模拟测试证明代码在受控响应下的行为，不能替代真实 Telegram 客户端、群组权限、媒体、API 删除限制或云端故障验收。

## 独立测试资源

使用两个不同测试 Bot、两套独立 Forum/授权管理员与实例资源。真实测试身份和群组只放私有 Environment。测试消息与删除范围仅限测试数据；不得清空真实用户私聊或管理员群组历史。

每次验收记录部署 SHA、实例别名、对应 Actions run 与实际结果到 PR 描述/评论，不把真实配置、消息正文、私聊身份或操作日志提交到仓库。区分模拟、云端配置读取、真实 Bot API 交互与人工 Telegram 客户端检查，未做的项目明确保留未验证状态。

## 业务验收

| 场景 | 应观察的结果 |
| --- | --- |
| 错误 Secret、无效 JSON、超大请求体 | 拒绝；合法更新持久提交后才确认；D1 故障不能伪报接收成功 |
| update/Queue 重复、乱序、DO 重建 | 不重复业务计数；按同用户持久任务顺序恢复，不因队列顺序误处理 |
| General `/tj`、旧话题绑定、切换/取消、占用 | 幂等；确认重新校验；General/日志话题禁绑定；保留历史和映射 |
| 资料变化、头像和三个资料链接 | 资料卡更新并置顶；首次联系不变；隐私/客户端限制如实说明 |
| 双向文字和全部约定媒体 | 实际投递、引用方向、逐条相册映射正确 |
| 编辑先于发送、编辑与删除并发 | 不覆盖较新内容，删除后不复活；不改管理员本人原件 |
| 成功、明确失败、拉黑、超时、429 | 分别记账；未知不自动重发；429 按平台返回延迟 |
| 反应失败 | 原发送/删除结果保留，只修复反应，不重发聊天 |
| 相册部分失败与 `/sc` | 摘要准确；单条 `/sc` 不扩展整组 |
| 清空确认前后新消息/积压/在途发送 | 快照覆盖已知私聊含封禁/失败/固定文案；新消息保留，旧积压不复活；管理员历史完全保留 |
| 封禁、伪造管理员/群组/按钮、过时卡片 | 用户静默；服务端拒绝越权或过时操作 |
| `/mb` 今日/7/30/全部与时区 | 按 UTC 原始记录与展示时区核对；重试/编辑/系统消息不计原消息量；未知独立列出 |
| 日志话题暂时不可写后恢复 | 审计保留、恢复后补报，无重复告警风暴 |

## 云端隔离与恢复验收

1. A/B 两个实例分别发送可区分的测试消息，核对其 Worker 版本、DB ID、Queue ID、DO namespace 均独立；操作 A 不改变 B 的消息、设置或积压。
2. 仅升级 A，检查 B 的 Worker 版本与业务状态保持一致；A 暂停期间入站仍可靠保存，恢复后按账本处理。
3. 在测试资源模拟请求已发出后中断、D1 结果写入失败、Queue 通知失败、Worker/DO 重建，核对没有盲目重复 Telegram 副作用。
4. 导出并解密测试数据库，核对 schema/业务/任务/操作账本完整；备份仅以加密形式离开 runner。
5. 在测试实例执行受控 D1 恢复演练，核对暂停闸门、全新恢复代次、旧任务隔离及未知项保留，最后再显式恢复。不能把单纯恢复 SQL 或 `/health` 200 当作恢复验收。

最终检查应与 [V4.0 验收清单](requirements-v4.md#181-验收清单) 对照。只有真实证据支持的项目才能报告完成。
