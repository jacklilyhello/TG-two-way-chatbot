# 排错、升级、回滚与数据恢复

## 单实例维护

从 main 运行 `Instance operations`，选择目标实例、已通过 main CI 的精确 SHA 与操作。每实例发布和维护共用 concurrency 锁，不并行修改同一实例。

| 操作 | 行为 |
| --- | --- |
| `status` | 鉴权读取版本、暂停状态、任务状态聚合和已发出操作数 |
| `pause` | 把出站暂停状态持久保存；入站仍落库，队列保留 |
| `recover` | 补唤醒当前代次可执行任务；旧代次未完成任务隔离为 quarantined |
| `resume` | 核对 Webhook 属于当前实例后显式恢复出站；不会清除未知操作记账 |
| `export` | 要求已暂停且已发出操作归零，导出此实例 D1 并加密 |
| `deploy` | 核对身份/资源，兼容迁移、单实例版本安装和可选 Webhook 配置；首次与升级均保持持久暂停 |

维护入口为 `POST /internal/maintenance`，使用实例 Webhook Secret 鉴权；不要把带 Secret 的请求复制到报告、工单或公开日志。健康入口 `GET /health` 仅返回必要状态与版本。

暂停是持久出站闸门，不会撤销已经发出的 Telegram 请求。恢复、回滚、导出前须等待在途请求完成并核对已发出操作数；无法确认的请求保留未知，不得手工改为成功或重新发送。

暂停后的 `pause` / `status` 每次最多核对 40 条已发出操作的 Bot DO 持久响应，并补写 D1 结果；此核对不执行聊天任务，也不调用 Telegram。已知结果照实恢复，孤立或缺失响应保持未知并封存，防止延迟请求随后重发。超过一批时重复 `status`，直到已发出操作归零；归零不表示未知结果已解决，恢复前仍须人工核查。

## 常见故障

| 现象 | 检查与处理 |
| --- | --- |
| Webhook 403 | 核对实例路径和 Secret；不要关闭鉴权 |
| Webhook 503 | 检查 D1 可用性；Telegram 应重试，不能伪报 200 |
| 200 但消息未出现 | 检查任务积压、暂停状态、绑定、封禁、Telegram 权限和未知结果；200 只表示可靠接收 |
| 消息已发送但无 👍 | 查看反应独立记录与群组反应许可；仅修复标记，不能重发内容 |
| 话题创建结果未知 | 保留操作记账，核对 Telegram 是否已创建；不要连续重复 `/tj` 制造新话题 |
| API 429 | 尊重 `retry_after`，检查共享管理员群组发送额度；不同话题不视为独立群组额度 |
| 日志话题删除/不可写 | 业务审计留在 D1；恢复权限，或在 General 用 `/mb logtopic 话题ID` 验证并指定专用日志话题，之后补报尚未发送的事件；未知日志结果保留人工核查 |
| Queue/DLQ 中有消息 | 队列只是唤醒，D1 任务账本决定业务状态；不能把 Queue ack 当作业务已完成 |
| Cloudflare 权限不足 | 查看失败步骤、HTTP 状态/数字错误码与 Account Token 作用域；已有只读权限不能证明写权限 |
| 创建途中失败 | 先只读核对确定资源名与 ID，把 ID 填入私有配置后继续；不清理数据库/队列或自动猜测重建 |

### 分段耗时与业务排队

耗时数据只写入实例私有 D1，不向公开健康入口、用户消息或普通日志输出消息正文、用户身份与操作参数。`jobs.first_started_at - created_at` 表示首次执行前等待，`completed_at - created_at` 表示整个任务生命周期，`execution_ms` 累计本地执行各次尝试的耗时。未完成或升级前没有采样的字段保持空值，不能推算成零。

`operations.call_started_at` / `call_finished_at` 保存首次调用尝试与确认结果时间；`call_attempts` 统计已准备向 Bot DO 发起的尝试，不能证明每次请求都已到达。`prepare_ms` 累计调用前账本查询、预备写入与暂停检查耗时，不含最后的 issued 标记写入；`transport_ms` 累计 Bot DO 往返耗时，`bot_wait_ms` 累计 Bot DO 内部串行等待及有界本地额度等待，`api_ms` 是最近一次实际 Telegram 请求的耗时，持久响应重读保留该原始值。`rate_wait_ms` 只累计退回任务调度的限流响应所要求等待的时间，并非真实睡眠时长；为零也不能证明没有本地额度等待。以上字段不能直接相加当作端到端耗时。浏览器上传与渲染时间另行实测。

Webhook 在 D1 提交后通过 `waitUntil` 直接提示对应 DO 持久设置 Alarm，避免首次执行完全等待 Queue 消费；此提示只安排唤醒，不等待业务投递。Queue 与 Cron 继续作为独立恢复入口。同一 Queue 批次合并重复用户键，并行唤醒不同协调器；每个用户的业务顺序仍由 D1 序号与对应 DO 保证。资料卡与反应使用独立持久任务，资料卡主动让当前用户业务积压先行，10 秒反应等待不会占住业务任务。业务发送及重试路径在回执和失败通知任务持久提交后，通过 waitUntil 保持 Queue/Alarm 唤醒提示存活；提示缓慢或失败不阻塞后续业务，D1 账本和恢复扫描继续兜底。

管理群的发送额度继续跨所有话题共享，每条消息保留 3100 毫秒间隔，相册按成员数量预留发送额度；私聊保持 1050 毫秒间隔。反应单独使用每群 1050 毫秒间隔，并共享 Bot 全局节奏。消息编辑、删除与取消置顶不发送新消息，使用独立维护额度，仍保持群组 3100 毫秒、私聊 1050 毫秒的保守间隔；置顶与话题操作继续占用原额度。所有类别共享 Bot 全局节奏和限流暂停，实际 API 开始时间用于保守更新额度，避免较慢的安全检查或持久写入缩短下次间隔。Telegram 的 `retry_after` 从收到限流响应开始计时，整个 Bot 的读写请求都遵守该暂停。突发输入允许持久排队，不能把发送限流导致的排队误判为丢失或通过盲目重试制造重复。平台依据见 [Telegram Bots FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)。

Bot DO 对剩余不超过 1000 毫秒的本地额度等待可在当前调用内短等，累计安排的等待最多 1000 毫秒、最多 4 次。等待会释放内部串行入口；重新进入时仍重读操作记账、暂停状态、绑定与授权检查及当前额度，真正出站前才标记 issued。已有本地额度等待时，暂停检查可能在短等后执行，但不会发出已暂停的请求。较长等待、平台 `retry_after`、维护暂停及清理优先等待继续交给持久任务调度，不能就地绕过。

普通论坛消息附带的话题创建服务根引用没有可映射的业务内容；仅在管理员当前绑定话题、服务标记与话题根 ID 一致且没有显式引用元数据时跳过映射查询和误报审计。真实业务引用、跨用户或失效引用继续按原有映射检查与安全降级处理。

日志按每批最多 12 条合并，由 Queue 提示和 system Conversation DO Alarm 唤醒，Cron 保留兜底。`audit_logs.reported=2` 表示自动补报已封存、需人工核账：既可能是外部日志发送未知，也可能是恢复代次边界的保守封存，不能等同于业务消息投递 unknown。更换恢复代次前，快照中尚未报告的审计会先封存；首次升级无日志代次标记且存在旧代次历史时，已有未报审计也可能封存。记录不会删除。日志批进入 `attention` 后，后续自动日志发送暂停，审计仍继续持久保存；双提示都失败且没有其他唤醒时，仍需 Cron 或明确 `recover` 兜底。

完全没有可核实代次归属的旧快照，必须通过下面的受控恢复工作流，先封存全部既有未报审计并保存新日志代次，再安装新代次。仅修改私有 `recovery_epoch` 并普通部署，不能证明旧日志从未发送，不作为此类快照的安全恢复流程。

Wrangler 默认会输出配置变量，部署脚本因此不转发其原始输出，并关闭 runner 的 Wrangler 磁盘调试日志，只保留操作阶段、退出码及可提取的 Cloudflare 数字错误码。需要进一步排查时在 Cloudflare 中只读查看精确资源，避免公开真实群组、管理员身份或完整配置。

## 升级与代码回滚

每个 Bot 单独升级；代码版本与 D1 schema/migration 必须兼容。正常升级不能清库、导入旧库或清除待处理任务。DO migration 从版本化 `wrangler.jsonc` 生成，禁止通过部署工具删除或转移 namespace。

回滚仍通过 `deploy` 选择之前已通过 main CI 的原生版本 SHA。先暂停并排清在途请求，核对该版本能读取当前 schema，再安装。工作流不会自动回退 D1，也不会恢复旧服务器消费者。首次上线尚无上一份原生业务版本时，保持维护暂停，继续接收持久更新或让 Telegram 重试，修复后恢复。

## 加密导出

1. 离线生成 age 密钥，只把公钥写入实例 Environment 的 `BACKUP_AGE_RECIPIENT`；私钥不进入 GitHub/Cloudflare Secrets、源码、报告或日志。
2. 运行 `pause`，等待在途请求排清，再运行 `status` 确认暂停且已发出操作为零。
3. 运行 `export`。SQL 只暂存于隔离的 Actions runner，使用 age 加密后仅上传 `database.sql.age`。加密失败不会上传明文。
4. 加密 artifact 默认保留 7 天；下载后按自己的保留政策放入私有离线存储。没有默认无限保存或自动删除业务记录的政策。
5. 在受控环境中用 `age --decrypt -i <私钥文件> -o <受保护SQL文件> <加密备份>` 解密。不要把业务数据库导入日常开发环境或公开 artifact。

R2 长期私有备份为可选扩展，当前工作流未创建 R2 桶。D1 Time Travel 的可用窗口以实际账户套餐为准，恢复前核对 [Cloudflare 官方说明](https://developers.cloudflare.com/d1/reference/time-travel/)。代码回滚不等于数据备份。

## D1 恢复边界

仓库故意不提供“一键覆盖生产数据库并自动续跑”的恢复动作。D1 回退不能同步回退 Queue、DO 或 Telegram：发送过的消息不会撤销，删除的私聊内容不会重新出现，旧任务重放会产生真实外部副作用。

恢复按以下受控流程执行，写入仍只能在单独评审的 GitHub Actions 恢复工作流中完成：

1. 对目标实例持久暂停；停止任何旧消费者/自动重启；排清在途请求，并保留当前 D1、队列、DO 状态与原生版本的备份。
2. 明确精确实例、数据库 ID、恢复书签/时间点或加密备份校验值、目标 schema 和版本。先在此实例专用测试资源验证 SQL/Time Travel 恢复及版本兼容，不能使用另一 Bot 的数据或 namespace。
3. 恢复业务数据库时保持出站关闭。恢复后的 D1 可能含暂停前快照，因此不能只依赖恢复前的 D1 `paused` 值；恢复工作流应先把暂停状态重新写入，或先部署 `PAUSED=true` 的维护版本并核对生效，再执行恢复。未确认闸门时不得开放旧队列/DO 调用。
4. 将私有配置 `recovery_epoch` 改为全新值并部署兼容维护版本。旧 DO 结果日志和队列不能当作新代次工作；旧代次未完成 D1 任务应先隔离，保留审计和人工核对列表，不能简单批量改成新代次。
5. 对照 Telegram 实际状态和恢复前操作结果，识别已确认完成、明确未发出和未知任务。已完成的不重复执行；未知进入人工核查；仅对证明未产生外部副作用的任务安排新的受控补偿。
6. 执行 `recover` 与 `status`，核对隔离、版本、绑定和日志，再显式恢复。新系统后续消息与统计从真实记录继续，不推算缺失历史。

`recover` 是持久任务唤醒/代次隔离工具，不是数据库恢复工具，也不会自动消除外部未知结果。未经测试的恢复流程不能标为“已完成恢复演练”。

### 独立测试实例恢复工作流

`Test D1 recovery drill` 仅允许 `test-a`、`test-b`，且所选 Environment 必须设置 `TEST_RECOVERY_DRILL_ALLOWED=true`。它不能用于正式实例，也不会自动恢复出站。运行前准备离线 age 私钥，在 Environment 的 `BACKUP_AGE_RECIPIENT` 只保存公钥；确认所选实例已经部署输入的完整 main CI 版本 SHA，并记录该实例 D1 的精确 Time Travel 书签。

将一个从未使用的新 `recovery_epoch` 私下保存到该实例的 `INSTANCE_CONFIG_JSON` Secret，将精确恢复书签保存到同一 Environment 的 `TEST_RECOVERY_BOOKMARK` Secret。工作流只输入书签和新代次各自的 SHA-256 摘要、当前部署 SHA，显式勾选仅恢复测试数据；脚本必须核对摘要与 Secrets 一致。真实配置、代次和书签不要写入源码、PR、公开工作流输入或普通日志。若工作流失败，先检查它停在哪个阶段和实际云端状态，不能盲目重跑恢复请求。

工作流先暂停并排清在途操作，再安装 `PAUSED=true` 的静态维护版本。维护版本让 Webhook 返回 503，Telegram 保留更新重试，避免恢复覆盖期间确认接收后又丢失新消息。工作流把当前数据库和恢复点加密，成功保存加密 artifact 后才单次请求恢复指定书签；随后应用兼容 migration、重写持久暂停，在同一事务内封存快照未报审计并记录新的日志代次，再部署全新代次并隔离旧任务。封存或读回未确认时保持静态暂停，不安装新代次或续跑。未知操作保持账本记录，不重放。

完成后下载加密备份并在受保护目录离线解密，核对 schema、业务记录和操作账本；检查聚合证据中的隔离与未知计数。实例此时仍静态暂停且 Webhook 返回 503。保留新代次私有配置，按普通 `deploy` 安装同一兼容版本，再执行 `status` 和显式 `resume`，最后用真实 Telegram 新消息核对无旧任务重复投递。任何阶段结果未知时，保持暂停并核查，不能把代码部署成功当作恢复成功。
